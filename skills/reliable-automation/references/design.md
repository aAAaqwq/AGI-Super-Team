# 设计说明：让 agent 团队"自动运转"缺的两件基础设施

本文是这个 Skill 的设计依据，也是它存在的理由。服务对象是**已经在自动运转
（或被要求自动运转）的 agent 团队**：一套明确的角色（本仓库就是 14 个 C-suite +
92 个叶子专家）、定时或事件触发的任务、判级 → 路由 → 执行 → 归档的流程。

所有反例都来自本仓库主人的真实事故记录（交易 / 采集 / 推送类常驻守护进程），
不是假想场景；agent 侧的推论则来自同一个根因。

## 主线论断

> **"持久稳定" ≠ "不失败"，= 失败了你知道 + 状态不丢 + 能重跑。**

落到 agent 团队上，这句话说的是三件很具体的事：

| 支柱 | 对 agent 团队意味着 | 缺了会怎样 | 对应工具 |
|---|---|---|---|
| 失败了你知道 | 定时/事件任务**跑了没有、跑成功没有** | "没消息"与"这次不需要跑"无法区分 | [`../scripts/watchdog.py`](../scripts/watchdog.py) |
| 状态不丢 | 产出必须落在 **agent 之外** | 会话一关，这次 run 等于没发生 | 落盘产物 + [`../scripts/heartbeat.py`](../scripts/heartbeat.py) |
| 能重跑 | 重复触发 / 失败重试不产生第二份副作用 | 重跑一次就多发一份报告、多花一份 token | [`../scripts/idempotency.py`](../scripts/idempotency.py) |

## 五条原理

### 1. 状态必须在 agent 之外

会话上下文一关就没了。agent 的"记忆"不是状态——它是**易失的运行时**。

所以团队的真实状态只能是这些东西：

- **落盘产物**：一次 run 的结论必须写到文件里（`sessions/<date>/<task>.md` 一类布局），
  否则这次 run 在人类看来等于没发生；
- **任务队列 / 台账**：谁排了队、跑到哪一步、下次该什么时候跑；
- **心跳**：没有稳定产物的长任务，至少要留下"我还在跑"的时间戳；
- **审批记录**：人工闸门点过头这件事，也必须是磁盘上的事实，不能靠人记得。

推论：**每个自动任务都必须有一个可以被外部检查的产出点**。如果一个任务既没有
产物、也不写心跳、也没有台账，那么它的健康与否在本设计里是不可观测的——
这不是工具的缺陷，而是任务本身缺少可观测的接口。

### 2. 静默失败必须可见（进程活着 ≠ 在工作）

`KeepAlive`、`Restart=always` 只解决"进程死了拉起来"。它们对**活着但卡死**的
进程完全无感：SSL 握手挂住、WebSocket 半开、上游返回空响应后进入重试死循环。

agent 侧是同一个问题的另一种形态：**"没有消息"必须能与"这次不需要跑"区分开**。
一次 run 跑完没产出、或者判定"跳过"却没说出口，人类看到的都是安静的界面——
和"今天确实没事"长得一模一样。

所以健康信号必须是**工作产出**，不是**进程存在**，也不是**任务的自我声明**。
这就是 `watchdog.py` 默认查产物 mtime、而不是查 PID 的原因。

#### 子节：配置错误与任务故障必须分开报

这是 `watchdog.py` 里最容易被忽略、但最影响可用性的一个决定。

如果"注册表指向的路径不存在"和"文件存在但太旧"都报成同一种 `stale`，会有两种坏结果：

- 一次路径写错 → 永久告警 → 运维开始忽略所有告警（告警疲劳）；
- 真正的任务停摆 → 混在一堆路径噪声里 → 同样被忽略。

所以路径不存在一律报 `config-error`：它说的是**注册表与磁盘现实不符**，
不等于任务坏了，处理方式也完全不同（改配置 vs 查任务）。
`watchdog.py` 把它和 `stale` / `empty` / `failed` 分开计数、分开显示。

代价是诚实的：任务**第一次**产出文件之前会报一次 `config-error`。
对周期性任务来说这通常是想要的（产物被清理/改名其实就是故障），
对首次启动的任务可以用 `"on_missing": "stale"` 显式声明"缺失即故障"。

> 注意：产物路径必须是**稳定的**。如果布局是 `sessions/<date>/<task>.md`，
> 要么让任务维护一个 `latest` 指针，要么让注册表本身由生成器重新生成——
> 否则每天都会因为"昨天的日期"报一次 config-error，把真正的告警淹掉。

### 3. 重跑必须安全（幂等）

自动运转的 agent 任务一定会被重跑：定时器重叠触发、队列重投、run 失败后重试、
崩溃恢复、时钟回拨。如果动作本身不幂等，重跑就是事故而不是恢复。

在 agent 团队里，重复执行的代价至少有三种：

- **副作用重复**：同一份报告发两次、同一条记录写两遍；
- **token 重复消耗**：一个已经很贵的 run 被重跑，账单直接翻倍；
- **状态互相覆盖**：两次并发 run 同时写同一个产物，后写的赢，前一次的证据丢失。

幂等键（`<task_type>:<entity>:<time_bucket>`）把"这个动作做过没有"从人的记忆
变成磁盘上的事实。**领到凭证才干活。**

### 4. 人工闸门：L3 级动作必须等人点头

自动化能把事情做完，不代表它**应该**把事情做完。发布、动资金、法律文件、
对外声明这类不可逆或高影响的动作，自动化只能准备到"待批准"这一步，
跨过去必须有人。

这条原理对基础设施的要求很容易被忽略：**闸门本身也要有状态**。
"等人点头"如果不落盘，就会出现"人已经批了但 agent 不知道"（重复问你）
或"agent 以为批了"（越权执行）两种失败。

幂等键天然适合当闸门凭证：

```bash
# L3 动作在人工批准后才允许执行：批准动作本身也领一次凭证
python scripts/idempotency.py --ledger ~/.local/state/agent-tasks/ledger.jsonl \
  claim 'approve:publish-2026-09-16:human' && ./publish.sh
```

### 5. 不能自证：跑任务的 agent 不能自己宣布完成

本仓库的 Governor 岗位契约写得很清楚：**不批准自己主要设计、实现或修改的工作**；
缺少证据统一标记为"待验证"；**无独立审查者可用时说明限制，不用"自审通过"替代独立性**。

这条原理落到本 Skill 上，是一个设计约束：

- `watchdog.py` 是**外部检查者**，它不读任务的自我声明、不解析"我已经成功完成"的
  文本，只看产物 mtime / 心跳时间戳 / 命令退出码；
- 任务自己说"成功"不算证据，**落盘的产出才算**；
- 同理，agent 团队里的重要完成声明应该交给独立角色复核（`ast-governor`），
  而不是由执行者自己在同一个会话里盖章。

## 三个真实反例

### 反例 1：6 小时静默断档

引擎里写的是 `except Exception: return None`，把全部异常吞掉。某天币安
`data-api` 端点 SSL 失败，异常照例被吞，系统进入"进程还在、什么都不做"
的状态：**6 小时零产出**，而 `launchd-realtime.err.log` 是 **0 字节**。

发现方式不是告警，是"我没收到消息"——也就是说，发现依赖人肉。

- 教训：错误日志为空不代表没出错（"0 字节"既可能是没出事，也可能是没记录）；
  `except Exception` 会把故障变成静默。agent 侧的同构写法是"捕获异常后返回一个
  友好但不含产出的空结果"。
- 本 Skill 的回应：`kind: "artifact"` 检查产物 mtime，60s 就能发现，
  且**不用改引擎一行代码**。

### 反例 2：假装的推送

`scanner.py` 里推送是这么写的：`subprocess.run([...])` 包在 `except: pass` 里，
而且命令里的路径**写死指向一个已经不存在的文件**。结果 `--telegram`
看上去一直在工作，实际上什么都没发出去。

- 教训：外部动作的"成功"必须由**外部证据**判定，不能由调用方自己声称。
  agent 侧的等价物：任务报告"已通知相关方"，而通知命令早就失效了。
- 本 Skill 的回应：这正是 `config-error` 与 `stale` 分开的原因——如果在
  `watchdog.py` 注册表里登记了这个推送产物，第一次运行就会得到
  `config-error：注册表指向的路径不存在`，把"路径写错了"和"任务变慢了"彻底分开；
  对没有落盘产物的动作，用 `kind: "command"` + 告警命令自身的退出码来判定。

### 反例 3：跑完了，但你看不出来

实测该机器上 6 个守护进程全部在跑，但：

- **没有任何一个**写"我还在工作"的信号；
- **没有 watchdog**。

那 6 个进程的工作状态对外完全不可见，能撑到今天靠的是主人自己盯着消息流。

agent 侧是同一个问题的另一种形态：一次 run 跑完没产出、或者判定"跳过"却没说出口，
人类看到的只是"没消息"。而"没消息"与"这次不需要跑"长得一模一样——
**于是这个团队无法无人值守，因为你不知道不用管它。**

- 教训：`KeepAlive` 保证的是进程，不是工作；会话保证的是上下文，不是产出。
- 本 Skill 的回应：`heartbeat.py` 让任务用一行代码接入心跳，
  `watchdog.py` 的 `kind: "heartbeat"` 负责读回来；产物型任务则直接登记 `artifact`。

## 取舍与已知盲区

### 谁来看 watchdog？

`watchdog.py` 是一次性进程，由 launchd / cron 定时拉起。如果它自己没被拉起、
或者告警命令本身坏了，异常仍然无人知晓。这是本设计的真实盲区，缓解方式：

- watchdog 也用 `kind: "command"` 登记自己（例如一条检查"上次巡检时间"的命令）；
- 告警命令的退出码会被检查，失败会体现在退出码上（`1`），由外层调度器记录；
- 更彻底的做法是让告警通道自己有心跳——超出本 Skill 的范围。

### 默认不推送

`--alert-cmd` 默认不执行任何东西。告警通道（Telegram / 邮件 / 工单）
是使用者的运维决策，本 Skill 不假设你有哪一种，也不写死任何一种。
工具只负责"把异常算出来并交出去"。

### 不做自愈，也不做闸门的业务判断

本 Skill 只做**发现**，不做自动重启、自动补单、自动修复，也不替你决定
哪一级动作需要人工批准。自愈需要护栏、停止条件和人工接管路径；
而"什么算 L3"是团队的治理决策，不是基础设施能代劳的。
在没有护栏之前，自动重启只会把"静默故障"升级成"静默重启循环"。

### 阈值怎么定

`max_age_seconds` 建议取正常产出间隔的 **3~5 倍**，并显式考虑跳过场景
（周末不跑的任务就该按周设，而不是按天）。定得太紧会抖动误报，
误报会直接导致告警疲劳——而告警疲劳是反例 1 能持续 6 小时的真正原因。

### 幂等键的时间桶是人的责任

`time_bucket` 取粗了会漏做（整周共用一个键 → 只做了一次），
取细了会重复做（每毫秒一个键 → 等于没有幂等）。脚本无法替你决定业务语义，
只能通过 `key_shape_warning` 提醒键的结构是否规范。

### `--gc` 的并发盲区

`gc` 用"写临时文件 + `os.replace`"重写账本，也就是**换 inode**。
如果此刻还有进程在往旧 inode 追加，它的写入会丢失。
所以 `gc` 只应该在安静时段跑（例如 cron 的凌晨任务），
或者干脆用 `ttl_seconds` 让旧键自然失效、不做物理清理。

### 只依赖标准库

不引入 pip 依赖是本仓库的房内风格：这些脚本要能在任何一台已经跑着守护进程 /
调度器的机器上直接用系统 Python 运行。`heartbeat.py` 的写入用 `os.replace`
保证原子性，`idempotency.py` 的追加用 `O_APPEND` + 单次 `os.write` + `flock`
保证不撕裂、不重复领取——两者都不需要任何第三方库。

## 接入顺序（agent 团队版）

1. 先给**已经有落盘产出**的任务登记 `artifact`，跑一次 `watchdog.py`；
2. 把 `config-error` 逐条修干净——这一步通常就能发现一两个"假装的推送"，
   或者一个根本没有产出的假任务；
3. 把 watchdog 挂到 launchd / cron（建议 5 分钟一次），接上告警出口；
4. 给没有稳定产物的长任务加 `heartbeat.py beat`，并把 `max_age_seconds`
   按它们的真实节奏（含跳过场景）设好；
5. 给"只该发生一次"的动作（发报告、写台账、L3 放行）加 `claim()`；
6. 最后才谈全自动：先有可见性，再谈闸门，最后才逐步放开自主执行。
   顺序反了的话，你不会知道自动化到底有没有在生效。
