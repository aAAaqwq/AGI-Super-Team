# 微信公众号长文机制

本文件综合用户提供的两篇第三方文章，只保存可迁移机制，不保存外部原文、签名句或独特口癖。

## 产品开源型主结构

```text
今天正在做的动作
  → 这个工具一句话做什么
  → 作者为何离不开它
  → 一次具体故障证明问题真实存在
  → 回答读者的合理质疑
  → 现有方案为什么不够
  → 用三到五部分解释新模型
  → 给出最小使用方式和完整流程
  → 升到人与 Agent 的分工
  → 回扣开头动作或故障
  → 最后才放地址、活动或行动引导
```

不要求每篇包含全部节点。短工具稿可压缩，但“真实故障、机制模型、操作方式、边界”四项不能同时缺失。

## 三次升维

### 从功能升到问题

不要停留在“它会做五件事”。先说明为什么旧信息、旧文档或旧流程会让 Agent 做错事。

### 从问题升到模型

把复杂项目压缩成职责不同的知识层或流程层，让读者明白错误在哪一层发生、该去哪一层修。

### 从模型升到协作观

最后回答更大的问题：什么应该持久化，什么必须由人判断，Agent 应该在哪些环节加速，哪些环节不能替代。

## 证据与图片的交替

长文不要连续讲抽象道理。建议按以下节奏循环：

1. 一个判断；
2. 一个真实场景或错误；
3. 一张过程、界面、数据或模型图；
4. 一句把读者拉回主线的话。

图片必须有用途说明。第三方素材、后台数据和账号信息必须先做权利与隐私检查。

## 产品说明如何不写成说明书

- 用第一次出错解释为什么需要功能；
- 用替代方案的缺口解释自己的设计选择；
- 用一个命令或最小动作降低使用门槛；
- 详细步骤保持编号，但每一步说明它防止什么错误；
- 社会证明只能作为补充，不能替代可验证结果。

## 方法论文章的双主线

方法论长文可以同时推进：

- 明线：如何构建、使用或迭代一个系统；
- 暗线：作者如何重新理解人和 AI 的分工。

两条线必须在一个真实故事里汇合。不要用抽象口号强行升华。

## 回扣而非复述

结尾不要重新列功能。回到前文的故障、选择或动作，展示作者现在会怎样做。Daniel 的回扣应来自自己的项目证据，例如字幕二次失败、导出事件未回传或授权质量门；不要借用外部作者的书架、固定短句或品牌口号。

具体结尾结构、互动层与六类原创结尾样本见 [公众号结尾系统](wechat-endings.md)。
