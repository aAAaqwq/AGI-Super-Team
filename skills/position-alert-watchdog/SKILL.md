# 持仓盯盘告警（cron no_agent + 动态阈值 + 每日去重）

用户的**持仓盯盘系统**：交易时段自动轮询持仓票行情，只在**新触发**关键位时推一条带动作建议的提醒，无新信号静默。

## 触发条件
- 用户说「盯盘提醒太频/太吵」「改成 N 分钟一次」（**用户明确偏好 30 分钟；10 分钟会刷屏，已被抱怨过**）
- 「加一只 XX / 成本 X」「把 XX 从盯盘里去掉」「成本价改成 X」
- 「关键位不对 / 这个提醒没意义 / 阈值过期了」
- 盯盘脚本报错、提醒里出现已经不可能的价位（例：现价 10.20 却提示"跌破今日低 11.44"）
- 任一盯盘提醒推送后用户直接回话（说明系统在跑，多数是在要求调参）

## 系统构成（2026-10-16 现状）
| 项 | 值 |
|---|---|
| 脚本 | `$AST_SCRIPTS_DIR/watch_positions.py` |
| 去重状态 | `$AST_SCRIPTS_DIR/.watch_positions_state.json`（按日重置，`{date, fired[]}`） |
| cron job | 名称 `持仓盯盘监控（当前持仓名单）`，`no_agent=true`，`script=watch_positions.py`，**`deliver` 显式写 `feishu:oc_<私聊id>`**，不要用 `origin`（见 Pitfalls） |
| 频率 | **用户指定 6 个时点**：`09:45 / 11:00 / 12:00 / 13:35 / 14:20 / 15:00`。cron 写 `*/5 9-15 * * 1-5` + 脚本内时点窗口判断（见「定时推送时点」节），**不要退回 `*/30` 均匀轮询** |
| 数据源 | 实时：腾讯 `qt.gtimg.cn`（GBK）· 日K：**多源 fallback（东财为主，新浪为备）**，见下方「日K 多源 fallback」；细节见 skill `ashare-stock-research` |

## ⭐⭐ 定时推送时点：6 个固定时刻（2026-11-11 用户明确指定）

用户不要「均匀轮询」，要**指定的几个时刻各推一次**：

```
09:45 ｜ 11:00 ｜ 12:00 ｜ 13:35 ｜ 14:20 ｜ 15:00
```

**cron 表达式的局限**：标准的 cron 一个 job 只能有一个（分,时）组合，没法写「9:45 和 11:00 和 13:35」。
**不要建 6 个平行 job**（难维护、容易漏改）。

**正确实现：cron 高频跑 + 脚本内时点窗口判断，不在窗口就静默退出。**

```python
TARGET_TIMES = [(9, 45), (11, 0), (12, 0), (13, 35), (14, 20), (15, 0)]
WINDOW_MIN = 5          # 目标时点后 5 分钟内算命中（配合 cron 每 5 分钟）

cur_min = now.hour * 60 + now.minute
hit_slot = None
for th, tm in TARGET_TIMES:
    if 0 <= cur_min - (th * 60 + tm) < WINDOW_MIN:
        hit_slot = (th, tm)
        break

if not os.environ.get("WATCH_FORCE") and hit_slot is None:
    return 0            # 不在目标时点 → 静默（no_agent 空 stdout = 不打扰）

# ⚠️ 12:00 是午休，必须放行，否则被交易时段 guard 拦掉
if not os.environ.get("WATCH_FORCE") and hit_slot != (12, 0):
    if not ((925 <= hm <= 1135) or (1255 <= hm <= 1505)):
        return
```

**三个必须处理的点**：

| 坑 | 说明 |
|---|---|
| **12:00 是午休** | 原来的交易时段 guard（925-1135 / 1255-1505）会把它拦掉。用户要 12:00 是想看**上午收盘快照**，所以对 `hit_slot == (12,0)` 单独放行，行情仍是 11:30 的收盘价 |
| **窗口 5 分钟 + cron 每 5 分钟** | `11:00` 由 11:00 那轮命中（差 0 分）✅，11:05 那轮差 5 分不命中 ✅（天然防重复）。**别把窗口开到 10 分钟**，否则同一时点会推两次 |
| **改完要重新同步 cron 副本** | `cp watch_positions.py $HERMES_HOME/scripts/`。脚本改完不同步，cron 跑的还是旧版（本会话实测：11:00 那轮仍是旧逻辑） |

**验证方式（不等到点）**：

```bash
# 1. 单独验证时点判断函数（伪造时间）
python3 -c "
TARGET=[(9,45),(11,0),(12,0),(13,35),(14,20),(15,0)]
for h,m in [(9,44),(9,45),(9,50),(12,0),(15,0),(15,5)]:
    cur=h*60+m
    hit=any(0<=cur-(th*60+tm)<5 for th,tm in TARGET)
    print(f'{h:02d}:{m:02d} → {\"触发\" if hit else \"静默\"}')
"
# 期望：09:44 静默 / 09:45 触发 / 09:50 静默 / 12:00 触发 / 15:00 触发 / 15:05 静默

# 2. 验证输出内容（绕过时点）
WATCH_FORCE=1 python3 watch_positions.py
```

## 改配置的流程（不要跳过验证）

### ⭐ 现行流程（2026-11-09 起）：只改 JSON

1. `read_file $AST_DATA_DIR/positions.json`，改 `cost` / `shares` / `stop` 三个字段。
   - 加持仓 → `positions` 数组加一条（必须有 `cost`）
   - 加观察股 → `watchlist` 加一条（**不要**写 `cost`）
   - 清仓 → 从 `positions` 移到 `closed` 并填 `closed_date`
2. **同步 cron 副本**（cron 只认这个目录，漏了会跑不起来或跑旧版）：
   ```bash
   cp $AST_SCRIPTS_DIR/watch_positions.py $HERMES_HOME/scripts/
   cp $AST_SCRIPTS_DIR/auction_watch.py  $HERMES_HOME/scripts/
   ```
3. 验证：
   ```bash
   rm -f $AST_SCRIPTS_DIR/.watch_positions_state.json   # 清去重，让本轮能重新评估
   cd $AST_SCRIPTS_DIR && WATCH_FORCE=1 python3 watch_positions.py
   # 每只票应只出现 1 条（优先级去重生效）
   cd $AST_SCRIPTS_DIR && TZ=Asia/Shanghai python3 auction_watch.py   # 竞价脚本
   ```
4. 回读 cron：`cronjob(action="list")` 看 `next_run_at` 是否北京时间、`last_status` 是否 ok。

### 手写规则时的语法（`rules` 仍需手动改脚本的少数场景）

1. `read_file $AST_SCRIPTS_DIR/watch_positions.py` 看当前 `_load_positions()` 生成的 `rules`。
2. 若要给某只票**特殊规则**（自动生成覆盖不到的），在 `_load_positions()` 里按 `code` 加分支，不要退回硬写 `WATCH` 字典。
3. `rules` 语法 `(op, level_spec, msg)`：
   - `op`：`">="`（涨到）或 `"<="`（跌破）
   - `level_spec` 关键字：`cost` / `prev_high` / `prev_low` / `today_high` / `today_low` / `ma5` / `ma10` / `ma20` / `ma60` / `limit_up` / `limit_down`，或直接写数字（如 `3.21`）
   - `msg` 里 `{v}` 会被替换成实际价位（写「📈 突破昨高 {v} → 走强，持有观察」这种"价位+动作"格式）
4. **验证**（关键）：
   ```bash
   cd $AST_SCRIPTS_DIR && WATCH_FORCE=1 python3 watch_positions.py   # 绕过交易时段 guard
   WATCH_FORCE=1 python3 watch_positions.py                           # 第二轮必须静默 → 去重生效
   ```
5. 配置改完后若想让**下一次运行就重新评估**（而不是继续沿用旧去重记录）：
   `rm -f $AST_SCRIPTS_DIR/.watch_positions_state.json`
6. 改频率：`cronjob(action="update", job_id=<list 查到的>, schedule="*/30 9-15 * * 1-5")`，同时更新 name/prompt 里的票名单；回读 `next_run_at` 确认是北京时间。
7. 回复用户时给一张「票 × 触发方向 × 触发位 × 动作」表 + 当前成本价一览，并请他确认成本价是否准确。

## 设计要点（改脚本时别破坏）
- **阈值必须全部动态算**，禁止硬编码当日价位：`prev_high=k[-2][3]`、`prev_low=k[-2][4]`、MA 由日K收盘算、`limit_up=prev*1.1`（round 2 位）。
- **每日去重**：`fired` 里存 `"{code}|{op}|{spec}"`，同一档位当天只提醒一次 → 避免"价位一直满足条件"导致的重复刷屏。副作用：价格跌破后反弹再跌破不会二次提醒（用户没要求改成每次穿越都提醒；要改就用冷却时间而不是无限重复）。
- **无新信号必须空输出**：`no_agent=true` 模式下 stdout 直接当消息投递，**空 stdout = 静默不打扰**。异常时 `print(..., file=sys.stderr)` + `sys.exit(1)`，这样出错才会变成告警而不是悄悄死掉。
- 有 alert 时末尾附一行「持仓概览：名称 现价(涨跌%) 盈亏±% | ...」，告警本身带现价/涨跌幅/盈亏——用户要的是**结论+可执行动作**，不是数字堆砌。

## 观察标的（无持仓）：cost=None（2026-10-26 新增）

用户常把「候选股买点」和「持仓告警」放同一个 job。让 `cost` 支持 `None`：

```python
"sz000002": {
    "name": "示例股D", "cost": None,          # ← 无持仓，只监控买点
    "rules": [
        (">=", "ma60",  "🟢 站上 MA60（{v}）→ 突破确认，可考虑买入"),
        (">=", 31.18,   "🟢 突破前高 {v} → 短期转强"),
        ("<=", "ma5",   "🎯 回踩 MA5（{v}）→ 买点观察区"),
        ("<=", "ma20",  "🎯 回踩 MA20（{v}）→ 更优买点"),
        ("<=", "ma30",  "🔴 跌破 MA30（{v}）→ 放弃"),
    ],
},
```

**必须同步改三处，否则 `TypeError: unsupported operand type(s) for /: 'float' and 'NoneType'`**：

```python
# ① 盈亏计算
cost = w.get("cost")
pnl = (price / cost - 1) * 100 if cost else None
summary.append(f"{name} {price:.2f}({chg:+.2f}%)" + (f" 盈亏{pnl:+.2f}%" if pnl is not None else " 【观察】"))

# ② 告警消息
pnl_s = f" 盈亏{pnl:+.2f}%" if pnl is not None else ""
alerts.append(f"【{name}】现价 {price:.2f}({chg:+.2f}%){pnl_s}\n  {msg.format(v=lvl)}")

# ③ levels() 里的成本衍生价位要短路
"cost_p3": round(cost * 1.03, 2) if cost else None,
"cost_p5": round(cost * 1.05, 2) if cost else None,
```

**买点标的的规则要写「买点 + 放弃条件」成对**，只写买点会让人在没有止损概念的情况下进场。

### ⭐⭐ 观察股禁用「站上 MA60」——已经在线上就会天天误报（2026-11-11 实测）

自动生成规则时给观察股写了 `(">=", "ma60", "🟢 站上 MA60 → 突破确认")`，
结果三只观察股（示例股D/东方创业/锋龙）**全部天天触发** —— 因为它们本来就在 MA60 上方。

更糟的一次：东方创业当天 **−5.74%** 大跌，脚本却推「🟢 站上 MA60 → 突破确认」——
**把下跌报成突破**，是会误导下单的假信号。

**根因**：「站上 MA60」是**事件**（那一天穿过），但 `>=` 是**状态**（一直成立）。状态型条件不能用来表达事件。

**改法**：观察股只用两种有意义的触发

```python
# ✅ 回踩买区：现价距 MA5 在 ±2% 内（状态判断，但区间窄，不会天天成立）
L["near_ma5"] = _ma5 if (_ma5 and abs(price / _ma5 - 1) <= 0.02) else None
rules.append(("near_ma5", "ma5", "🎯 回踩 MA5（{v}）→ 买点观察"))

# ✅ 涨停：本来就该单独提示
rules.append((">=", "limit_up", "🔥 涨停（{v}）→ 强势，看能否连板"))
```

`near_ma5` 是**虚拟档位**，要在 `levels()` 里算好放进 L，规则循环里特殊处理：

```python
if spec == "near_ma5":
    lvl = L.get("near_ma5")
    if not lvl:
        continue          # 不在回踩区，跳过
else:
    lvl = L.get(spec) if ... else float(spec)
```

**通用教训**：写触发条件前问一句「这个条件在『什么都没发生』的日子里成立吗？」——
成立的就是状态条件，不能当事件用。

## 价位显示精度

`msg.format(v=lvl)` 直接塞 float 会打出 `30.404833333333332`（MA 是均值，必然带小数）。按价格量级分档：

```python
if isinstance(lvl, float):
    lvl = round(lvl, 3) if lvl < 5 else round(lvl, 2)   # ETF(<5元) 3 位；个股 2 位
```

## Pitfalls

- **⭐ 盘前/盘中的「昨高昨低」取值不同（2026-10-21 踩坑）**：`kline()` 返回的最后一根 K 线，
  **盘前是「昨天」、盘中是「今天」**。用固定 `k[-2]` 取昨低，盘前会取成「前天」，导致误报
  （实测：示例股C真实昨低 8.50，盘前却报「跌破昨低 8.88」并推了减半提醒）。
  正确做法：
  ```python
  today = datetime.now(BJ).strftime("%Y%m%d")
  quoted_today = str(f[30])[:8] == today and float(f[3]) > 0 and float(f[33]) != float(f[34])
  ref = k[-1] if not quoted_today else k[-2]   # 盘前取 k[-1]，盘中取 k[-2]
  ```
  判断「是否已开盘」不能只看时间，要看**行情时间戳（f[30]）是否为今天且高低价已分化**（盘前高=低=开）。

- **⭐ 规则价位不能坐在涨停价上方，否则「开板/回落」类规则会立即误触发（2026-10-27 踩坑）**：
  给观察标的写「回落就给机会」时写了 `("<=", 17.50, "🟢 回落到 17.50 以下 → 开板给机会")`，
  但那票当天**收盘就是涨停 17.22** —— 17.22 ≤ 17.50 恒成立，试跑立刻误报。
  **根因：「回落」是相对涨停价说的，但条件是绝对数字。**
  ```python
  # ❌ 涨停 17.22 时恒真
  ("<=", 17.50, "回落到 17.50 以下 → 开板给机会")
  # ✅ 阈值必须坐在涨停价下方，且离得够远（< 涨停价 × 0.99）
  ("<=", 16.90, "跌到 16.90 以下（开板回落）→ 有换手才看")
  # ✅ 或者直接用关键字，让脚本按当日核算
  ("<=", "limit_up", ...)   # 注意封板时 price == limit_up，仍会触发，需配合「是否封板」判断
  ```
  **自查方法**：加任何 `<=` 规则前，先算 `limit_up = round(昨收*1.1, 2)`，确认阈值 **< limit_up**；
  加任何 `>=` 规则前确认阈值 **> limit_down**。否则该规则必然每天第一时间触发。
  **通用教训**：`<=`/`>=` 的语义是「跌破/涨到」，但脚本只做数值比较 —— **语义方向和数值方向必须一致**，
  写「回落」「反弹」「开板」这类相对词时尤其容易错。

- **`>= cost` 这类规则每天都会触发一次**（因为 state 按日重置）。如果成本线在现价下方，
  用户会每天收到一条「回到成本 → 保本走」。这是**设计使然**，不是 bug —— 但如果觉得吵，
  改成 `cost * 1.03`（+3% 才提醒减仓）。

- **硬编码价位会随着股价下跌而失效**：瑞康原设 `>= 3.21`，跌到 2.96 后这条永远触发不了。
  改成动态引用（`prev_high` / `ma10` / `ma60`）才能长期有效。

## Pitfalls（续）
- **硬编码阈值是这类系统最大的坑（本会话踩实）**：原配置里「跌破今日低 11.44 → 减半」是 10/14 那天的低点，到 10/16 现价已 10.2，条件恒成立 → 每 10 分钟推同一句话，用户直接来抱怨"提醒太频"。**看到"每轮都推、内容一模一样"就是这个病，不是频率问题**。
- **no_agent cron 忽略 shebang**：非 `.sh` 脚本由 runner 自己的 Python 解释器执行，所以 shebang 写了不存在的路径（例：`#!$AST_DATA_DIR/.venv/bin/python`）不影响 cron，但手工执行会 `No such file or directory` (exit 127)。统一写 `#!/usr/bin/env python3`；本机 venv 在 `/opt/hermes/.venv`。
- **腾讯日K字段顺序是 `[date, open, close, high, low, volume]`**（不是 OHLC）：昨高取 `k[-2][3]`、昨低取 `k[-2][4]`。首根可能是当日未收盘 K。
- **`read_file` 曾把该 UTF-8 脚本判成 binary**（文件含中文注释、行首 `#!/...`）。此时用 `read_file` 重试/`patch`/`write_file` 覆盖都可行，纯读用 `terminal` 跑 `python3 -c "print(open(p,encoding='utf-8').read())"`。
- 规则里的 `cost` 关键字依赖 `WATCH[code]["cost"]`，**新增股票必须带上成本价**（用户口头给的成本价 = 配置里的 cost，不要自己推）。成本是"回本提示"档的唯一来源。
- 别自作主张加止损纪律提醒（例"跌幅 >-5% 无条件离场"）——用户的纪律是他自己的硬约束，改动要问。

- **⭐ `deliver="origin"` 发的是「创建那个 job 的会话」，不是「当前私聊」**（2026-10-21 踩坑：一个早前在 A2A 群里创建的套利监控 job，每天早上 9:00 往群里推，用户直接质问「为什么在群里推这个」。同时他发现该 job 输出已经烂掉——`批量周期：None 天`——所以一并删掉了）。
  **结论：私人类监控（持仓、套利、个人提醒）一律显式 `deliver="feishu:oc_<私聊id>"`**；团队类（日报/候选人/Token 统计）才写死群 id。`origin` 只在「服务端能保证创建上下文正确」时才安全。
  另外：用户对跑偏的 job 不宽容，宁可直接删。删之前最好顺手说明「为什么它跑到群里了」，否则用户会以为是新问题。

- **⭐ 动嘴之前先 `cronjob(action="list")`（2026-10-21 被用户反问「之前不是有吗」）**：本会话在给完操作建议后顺口问「要不要设成盯盘告警」，用户直接反问——因为这个 job 早就存在，而且**已经包含全部票、阈值还是动态算的**，比我要新建的方案更好。
  **规则：任何「要不要我新建一个定时任务/脚本/告警」的提议之前，先 list 现有 cron + 搜 `$AST_SCRIPTS_DIR/`。** 已有的话，正确动作是**改它**（核对阈值是否过期、票是否该增删），不是新建一个平行的。
  顺带：**阈值"过期"≠ job 失效** —— 动态阈值（MA/昨高低/涨跌停）不会过期；只有硬编码价位才会。用户抱怨"阈值不对"时先分辨是哪一种。

- **⭐⭐ 用户问「今日持仓怎么操作」时，先看现有 cron 有没有已经跑过（2026-11-09 被反问「不是有这个cron吗竞价的」）**：
  本会话用户问多维度分析持仓，我手工重做了一整套（拉行情、算四维共振、拉筹码、查外围），
  用户直接反问「不是有这个cron吗竞价的，不是动态根据我持仓股来分析的吗」。
  **规则：任何「分析持仓」类请求，第一步是 `cronjob(action="list")` 看有没有竞价/盯盘 job 今天已经跑过、或即将跑（`next_run_at` 在今天 9:26）**：
  - 已跑过 → 直接引用它的输出（或复述结论），再补它没覆盖的维度（外围/筹码/资金），**不要从零重做**。
  - 即将跑 → 告诉用户「X 分钟后自动推」，只补它不覆盖的部分。
  - 真正该做的是**检查 job 的配置是否过期**（持仓股数/成本/关键位），而不是绕过它手工分析。
  这条和下面「建新任务前先 list」是同一个病的两面：**系统已有能力时，先修系统，再回答。**

- **持仓平仓后必须同步移除 WATCH**：用户说「其他我都平仓了」时，除了改剩余票，还要把已平仓的从 `WATCH` 删掉，否则规则空转、每天推已清仓的票。删完同步改 cron 的 `name`/`prompt` 里的票名单。**如果用户没说，也要主动问一句「这三只还留着监控吗」。**

- **`(">=", 0.01, msg)` 是「每日一次必提醒」的标准写法**：用于「不管什么价格，今天都该处理」的场景（如业绩暴雷股开盘就清仓）。靠 state 按日去重 → 一天只响一次，不会刷屏。比写「开盘时间判断」简单可靠。

- **⭐⭐ 用户口述的「成本价」必须交叉验证，不能直接写进 cost（2026-10-29 踩实，后果严重）**：
  用户说「示例股B我买入了 12.7」「湖南天雁 8.0」，我直接按口述写进 `WATCH[...]["cost"]`。
  后来他发来券商持仓截图，**真实成本是示例股B 13.527、湖南天雁 8.001** —— 示例股B差了 6.5%。
  后果：我一路告诉他「你赚 +2.83%」，实际是「亏 −3.60%」，**而他是按我的话做买卖决策的**。

  **规则**：
  1. **用户发过持仓截图时，一律以截图为准**，口述只当参考；两者差 >2% 必须主动指出并请他确认，不要默默选一个。
  2. **没有截图时**，先在 `references/watch-positions-config.md` 和 `$AST_SCRIPTS_DIR/.watch_positions_state.json` 里找历史 cost；与口述不一致就明说「上次记录是 X，你说 Y，以哪个为准」。
  3. **盈亏百分比的绝对数值比方向更重要** —— 说「你在赚」和「你在亏」是两套完全不同的操作建议（止盈 vs 止损）。成本错 6% 足以把结论翻面。
  4. 加仓/摊薄后成本会变（示例股A 24.18 → 22.200），**用户没提也要问一句「成本有变化吗」**，否则所有 cost 衍生档（`cost_p3`/`cost_p5`/回本提示）全错。

- **⭐⭐⭐ 股数没变但成本涨了 = 券商「摊薄成本」口径，不是数据错（2026-11-11 实测，直接改变结论）**：
  用户发来截图：示例股A **200 股，成本 24.195 → 28.020**，股数一股没动。
  我在同价做 T 的假设下怎么算都对不上（同价买卖成本应不变），最后确认是**券商的摊薄成本口径**：
  卖出部分实现的亏损被摊到剩余持仓上，显示的 28.020 是「整体不亏」的保本价，不是加权买入均价。

  **为什么这条重要**：两种口径给的操作建议**完全相反**。

  | 口径 | 回本价 | 需涨幅 | 需要几个涨停 |
  |---|---|---|---|
  | 加权均价 | 24.195 | +35.5% | 3.1 个 |
  | **摊薄成本** | **28.020** | **+56.9%** | **4.7 个** |

  **➜ 看到「股数不变、成本变高」时：**
  1. **不要在盈亏数字上纠结「怎么算出来的」** —— 先确认口径（问用户或看券商设置里有没有「摊薄成本」开关）。
  2. **一律按截图上的成本给建议**（用户看的就是这个数，回本心理价位也是这个），JSON 里 `cost` 就写屏幕上的值。
  3. **成本大幅上移必须主动改策略**：回本需要 5 个涨停的票，策略要从「等回本」转成「逢反弹减仓换强票」——
     不说这句，用户会一直在等一个不可能的价格。
  4. 记录 `realized_pl` 到 `closed` 或 notes，方便日后回溯「这笔实际亏了多少」。

- **⭐ 用户重发持仓截图时，逐项核对「持仓 / 可用」两列**：`持仓 400 / 可用 200` 说明**今天买过 200 股（T+1 未解禁）**，
  也就是当天有加仓动作 —— 这时成本一定变了，且当日不能全卖。看到这两列不等就主动问。
