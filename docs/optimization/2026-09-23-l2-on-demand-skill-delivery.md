# L2 提案：665 个未分配 Skill 的按需获取

> 对应改造计划的[阶段 3](./2026-09-23-restructure-plan.md)。
> 本文是**提案，未实施**。它需要一次用户决策才能动手：**665 个放哪**。
> 结论都带可复现的数字或命令；不确定的地方明确标为「待验证」。

---

## 一、问题

`skills/` 下有 834 个物理 Skill 入口。安装器只复制其中的 **169 个**（团队已分配集），
判定依据在 `bin/installer/catalog.mjs`：

```js
const skillNames = canonical ? assignedSkills.all : catalog.curatedSkills;
```

`canonical` 来自 `config/cli-adapters.json` 的 `skillSource === "canonical-assigned"`，
当前有 5 个目标声明它（claude-code / codex / dsh / hermes / openclaw）。

复现：

```bash
node -e '
const fs=require("fs");
const m=JSON.parse(fs.readFileSync("config/team-manifest.json","utf8"));
const all=new Set();
for(const a of m.agents) for(const t of ["required","optional","harnessSpecific"]) for(const s of a.skills[t]) all.add(s);
console.log("assigned", all.size);'
# assigned 169
```

于是剩下 **665 个**处于一个尴尬位置：**它们在包里，但安装器不复制，也没有检索之外的获取路径**。
`npm run check:team-index` 生成的 [`docs/reference/team-index.md`](../reference/team-index.md) 第 7 节
就是给读者交待这件事的地方 —— 那里现在只能写「npm 包里有整棵树，自己复制」。

**这不是切分错误。** 169 与 665 的划分已经正确：前者是角色职责内的方法，后者是工具箱。
缺的是工具箱的**获取路径**。

---

## 二、硬约束：ADR-0008（不可绕过）

[ADR-0008](../adr/0008-ship-complete-skills-directory.md) 决定**全量打包 `skills/`**，
理由是此前半个 Skill（有 `SKILL.md`、没有 `scripts/` 与 `references/`）就是**坏产品**：
正文会引用自己的 `references/patterns.md`、`scripts/…`，只带入口的包让读者撞上一个跑不起来的命令。

因此本提案的每一条路径都必须满足：

> **要么整目录带，要么不带。任何方案都不得只传 `SKILL.md`。**

这条约束同样适用于 665 个 —— 它们和 169 个没有区别，都是完整目录。
任何「只下入口、正文里给个仓库链接」的机制已被 ADR-0008 评估并否决，不重新讨论。

## 三、三种存放方案的取舍

| | (a) 独立 npm 包 | (b) 独立仓库 | (c) 留在本仓库，排除出 npm |
|---|---|---|---|
| **形态** | `agi-super-team-skills`，只含 665 | 新 git 仓库，`skills/` 全量或 665 | 本仓库不动，`.npmignore` 排除 665 |
| **npm 包体积** | 主包只带 169，显著变小 | 主包只带 169 | 主包只带 169 |
| **git 用户体验** | 仍要装第二个包 | 要 clone 第二个仓库 | **无需变化**：clone 本仓库就有全部 834 |
| **按需获取** | 天然：`npm i` 单个包 | 需要 sparse-checkout 或整仓 clone | 不解决：包外的东西 npm 装不到 |
| **版本耦合** | 需要一个发布纪律：两个包版本必须同源 | 两个仓库要同步 commit | 无（同一棵树） |
| **ADR-0008 合规** | 合规（整目录进第二个包） | 合规（git 里本来就是整目录） | 合规（排除的是整目录，不是入口） |
| **主要风险** | 双包版本漂移：用户装了 v1.7 主包 + v2.0 skills 包 | 双仓库漂移；作者明确不想要第二个仓库 | **不解决用户问题**：npm 用户拿不到 665 |
| **落地成本** | 中：新 `package.json` + 发布流程 + 一个「哪个 skill 属于哪包」的生成器（数据已在 manifest 里） | 低（建仓 + 同步脚本），但长期维护成本高 | 低（改 `.npmignore`），但只解决体积，不解决获取 |

**判断（不是结论，是待你拍板的倾向）**：

- **(c) 单独用不成立** —— 用户明确要的是「665 按需获取」，而不是「665 消失」。
  它只能作为 (a) 的**伴随动作**：主包从 834 瘦到 169，是 (a) 带来的结果，不是独立方案。
- **(b) 与仓库现状冲突** —— 本仓库刻意是「一个仓库、一个契约层、一棵内容树」。
  引入第二个仓库会把「哪个是权威」变成日常问题，而版本耦合的成本由你长期支付。
- **(a) 最贴合既有结构** —— 615 个 Skill 的分配数据已经全在 `config/team-manifest.json` 里，
  「哪些进 skills 包」是**可生成的**，不需要人工维护第二份清单。
  代价是双包发布纪律，这一点必须在实施时用一个生成器 + 一个 check 钉死（见第四节）。

> 我对 (a) 的倾向是**有条件的**：只有在「主包只带 169、skills 包带其余」这件事由生成器决定、
> 且两个包的版本一致性由 CI 强制时，(a) 才比 (b) 便宜。否则 (b) 的漂移风险反而更低
> —— 因为它至少没有「同名不同内容」的版本歧义。
> **这条我无法凭仓库内证据定论，需要你按发布实际负担选。**

## 四、获取命令的形态

用户要「一条命令」。现有 CLI 入口是 `bin/agi-super-team.mjs`（`bin.agi-super-team`）。

### 形态建议

```bash
npx agi-super-team --skills <id>        # 取单个 Skill
npx agi-super-team --skills <id1>,<id2> # 取多个
npx agi-super-team --skills --list      # 列出可取（= 665 + 169）并标注归属
```

**必须遵守的三条**（否则这条命令会重造 ADR-0008 记录的那个坏产品）：

1. **落地的是整目录**：`SKILL.md` + `scripts/` + `references/` + `assets/` 一次到位，
   与 `npx agi-super-team install` 复制 169 个时用的是同一段逻辑（`planSkills`）。
2. **校验物理入口**：目标 Skill 必须在 `skills/<id>/SKILL.md` 存在。
   169 个在生成阶段就被校验过 —— 清单里任何缺失入口都会让
   `scripts/build_agent_skill_indexes.py` 直接报错；665 个不能例外。
   取一个不存在的 id 必须失败并列出近似候选，而不是静默成功。
3. **不写全量索引**：命令只取用户点名的那几个目录。把 834 个 description 一次性写进用户的
   harness 目录，正是这次改造要修的问题。

### 与现有命令的关系

- `install` / `connect` / `doctor` / `list-teams` 的语义不变：它们服务「团队」这条路径。
- `--skills` 服务「工具箱」这条路径，**不修改**任何已安装的团队文件。
- 两条路径的边界应当写进 `--help`：**装团队走 install，取个别能力走 --skills。**

### 待验证项

- `bin/agi-super-team.mjs` 的参数解析目前没有 `--skills`，实施时需要确认它与
  `--list-tools` / `--list-teams` 的互斥关系（未读全该文件的参数处理分支）。
- 从 npm 分包的形态取 665 个时，`npx` 需要先解析到 skills 包的版本；
  这一步在 (a) 方案下是新的失败点，必须有明确报错（「skills 包未安装 / 版本不匹配」），
  不能表现为「文件不存在」。

## 五、实施前置条件（缺一不可）

| # | 条件 | 为什么必须 |
|---|---|---|
| 1 | **用户决策 665 放哪**（(a)/(b)/(c)） | 决定全部实现方式，见第三节 |
| 2 | **需要一个生成器**：从 `config/team-manifest.json` 生成「主包清单 / skills 包清单」 | 手工维护两份清单必然漂移；这正是本仓库反复出现的那类问题 |
| 3 | **一个 check 钉死一致性**：两个包的版本号必须同源，且两份清单并集 = 834、交集 = 169 | 双包方案唯一的真实风险就是漂移，必须机器可判 |
| 4 | **一个回归测试**：随机取一个未分配 Skill，落地后其 `references/` 与 `scripts/` 齐全 | 直接对 ADR-0008 的坏产品场景做回归 |
| 5 | `package.json` 的 `files` 从 `"skills/"` 收紧为按清单排除 | 主包体积收益的唯一来源 |

**条件 2–5 全部是两个包（或主包 + 排除）共有的**，与 (a)/(b)/(c) 的选择无关 ——
也就是说第三节的决策不会推翻本节的清单，只会改变分发通道。

## 七、一句话

> 665 个不是垃圾，是**没有取货口**的库存。
