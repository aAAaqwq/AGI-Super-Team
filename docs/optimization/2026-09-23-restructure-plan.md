# 改造计划：从「平铺的仓库」到「层层递进的索引」

> 目标（用户原话）：**让 agent 着重索引团队精华（14 agents + 169 skills），其余按需获取。
> 摒弃噪音，创建层层递进的索引 —— 既引导 agent，也引导用户快速开始。**
> **拆解，而不是精简。**

---

## 一、诊断：问题不是"内容不好"，是"内容平铺"

```
产品层（契约+安装器+适配器）   580 文件   10%
内容库（skills/）           4433 文件   82%
其中：团队分配              169 个      ← 精华
      未被分配              665 个      ← 工具箱
```

**三类读者，同一份平铺内容：**

| 读者 | 他要什么 | 他现在看到什么 |
|---|---|---|
| **Agent** | 团队有谁、我该叫谁 | 全部 skill 的 description 一起进上下文 |
| **用户** | 这是什么、怎么装、怎么触发 | README 495 行（用户向 + 维护者向交错） |
| **浏览者** | 有哪些能力、怎么取 | `docs/` 110 个文件，无入口；834 个 skill 一起下载 |
| **贡献者** | 规矩是什么、怎么验证 | 8 对 build/check 没有对照表 |

**第一性**：一份内容服务四个人，就服务不好任何一个人。

---

## 二、好消息：切分已经做了一半

安装器**已经有正确的概念**，只是没被当成产品结构用：

```js
// bin/installer/catalog.mjs
const skillNames = canonical ? assignedSkills.all : catalog.curatedSkills;

// config/cli-adapters.json
{ "id": "claude-code", "skillSource": "canonical-assigned",
  "skillPaths": [".claude/skills"] }

// 且代码硬断言：5 个主力 harness 必须声明 canonical-assigned
```

```
assignedSkills.all = 169   ← 「团队」已正确切分，安装的就是它
未分配的            = 665   ← 「工具箱」，在包里但不装
```

> **所以不需要重新设计切分逻辑。需要的是：把"169 装、665 不装"这个既成事实，
> 变成对用户和 agent 都清晰的两条路径。**

## 三、目标架构：四层递进索引

```
┌─ L0 · 30 秒 ──────────────────────────────────────────────┐
│ 读者：用户                                                 │
│ 内容：一句话 + 一条命令 + 一个触发示例                        │
│ 载体：README 第一屏 · npx preview 摘要                      │
│ 退出条件：他知道装什么、装完怎么用                             │
└────────────────────┬─────────────────────────────────────┘
                     ▼
┌─ L1 · 5 分钟 ─────────────────────────────────────────────┐
│ 读者：用户 + Agent            ★ 精华层 ★                    │
│ 内容：14 agents + 169 skills（按 C-suite 分组）             │
│       "遇到 X 类问题找谁" / "每个角色配哪些方法"               │
│ 载体：agi-super-team-orchestrator skill · CATALOG.md        │
│ 退出条件：Agent 能自答"我该叫谁"；用户能自答"我能让它干什么"     │
└────────────────────┬─────────────────────────────────────┘
                     ▼
┌─ L2 · 按需 ───────────────────────────────────────────────┐
│ 读者：浏览者                                                │
│ 内容：全部 834 个能力的可检索目录（169 + 665）                │
│ 载体：catalog/（已存在）→ 补一条「怎么取到没装的」             │
│ 退出条件：他想要的 skill 有一条明确的获取命令                   │
└────────────────────┬─────────────────────────────────────┘
                     ▼
┌─ L3 · 维护者 ─────────────────────────────────────────────┐
│ 读者：贡献者 + 三个月后的你                                  │
│ 内容：ADR / plans / optimization / 8 对 build-check 对照表   │
│ 载体：docs/（已存在）→ 补一个真入口                           │
└───────────────────────────────────────────────────────────┘
```

**关键规则**：**每一层都只讲自己那层，并用一行指向下一层。**
现在的问题是 L0/L1/L3 全混在 README 的 495 行里。

---

## 四、改造分四阶段

### 阶段 1 · 让 L0 真的能用（最高优先，成本最低）

**问题**：新手入口走错路径；preview 是 515 行墙；覆盖用户文件不警告。

| 动作 | 状态 |
|---|---|
| `STARTUP.md` / `setup.md` 入口修正 | 🚧 修复中 |
| README 过期版本陈述 + 降级建议 | 🚧 修复中 |
| preview 改摘要 + 覆盖警告 | 🚧 修复中 |

**验收**：一个没读过源码的人，30 秒内知道"装什么、装完怎么触发"。

### 阶段 2 · 让 L1 成为"精华索引"（核心）

**这是用户说的"让 agents 着重索引团队部分"。**

| 动作 | 说明 |
|---|---|
| **建 `CATALOG.md`（或让 orchestrator skill 承担）** | 14 agents + 169 skills，**按 C-suite 分组**，每组：这个角色管什么 / 它配哪些方法 / 什么情况下叫它 |
| **确认 agent 侧加载的是 L1 而非全量** | 169 个 skill 的 description ≈ 19K tokens。要核实**未安装的 665 个是否会进上下文**（若会，这是真 bug） |
| **`connection.json` 补 delegates** | 现在默认安装后 11 个 manager 的 `delegates` 全是 `{}` —— 专家层是空的 |

**验收**：Agent 收到一个任务，能从索引里自答"该叫谁"；用户能看懂"这个团队能干什么"。

### 阶段 3 · 让 L2 可及（"拆解"的落地）

**现在**：665 个未分配的 skill 在 npm 包里（占了包体积的大部分），但装不上也不可检索。
**目标**：它们**不占包体积**，但**有一条明确的获取路径**。

| 动作 | 选项 |
|---|---|
| **npm 包只带 169** | 从 49 MB → 约 5 MB |
| **665 个的存放** | (a) 独立 npm 包（`agi-super-team-skills`）(b) 独立仓库 (c) 保持在本仓库但用 `.npmignore` 排除（git 用户仍能拿到） |
| **获取命令** | `npx agi-super-team --skills <id>` 或 `npx agi-super-team add-skill <id>` |

> ⚠️ **注意 ADR-0008 的约束**：那份 ADR 决定"全量打包"，理由是**此前半个 skill（有 SKILL.md 没 scripts/）是坏的**。
> 所以阶段 3 **不能简单地"只打包 SKILL.md"** —— 要么整包带、要么不带，**不能带半个**。
> 这条约束在 665 个上同样成立。

**验收**：npm 包 < 10 MB；用户能一条命令取到任意 skill，且取到的是完整的。

### 阶段 4 · 让 L3 可导航（维护者效率）

| 动作 |
|---|
| 8 对 build/check 的**对照表**（哪个生成什么、什么时候必须跑） |
| `docs/` 的真入口（现在 `docs/README.md` 是中文写的，且 110 个文件无分层） |
| 派生数据「谁消费」清单 → 决定哪些可以不入库 |

## 五、优先级与依赖

```
阶段 1  ████████  最高（成本最低，且是用户的第一印象）
阶段 2  ██████    核心（用户点名的"精华索引"）
阶段 3  ████      价值最大但最复杂（涉及 ADR-0008 的约束）
阶段 4  ██        维护者效率，可缓
```

**依赖关系**：
- 阶段 2 不依赖任何东西，可以立刻做
- 阶段 3 依赖一个决策：**665 个放哪**（独立包 / 独立仓库 / git-only）
- 阶段 4 独立

## 七、一句话

> **这个仓库不缺精华 —— 缺的是让精华"可被找到"。**
> 169 个 skill 已经切好了、14 个 agent 已经就位，**但没有任何一层告诉读者"这就是精华"**。
> 四层索引的作用，就是让每一类读者只看到自己那层，并且知道怎么往下走。
