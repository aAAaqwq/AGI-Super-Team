# 第一性原理分析：为什么这个仓库反复出现"检测到了但没修"

> 方法：`first-principles-thinking`。症状 → 隐含假设 → 第一性真相 → 重建解法。
> 姊妹文档：[2026-09-23 冗余与质量审计](./2026-09-23-redundancy-audit.md)（数字与复现命令）

---

## 一、问题（用事实陈述，不用形容词）

```
2026-09-21  viral-product-demo 加入 → 漏跑 4 个生成器 → CI 红
2026-09-23  才发现（2 天）
```

而这不是第一次。同一模式的三次独立出现：

| 时间 | 事件 | 检测 | 结果 |
|---|---|---|---|
| 2026-09 之前 | npm 从未发布过 tag | 有诊断文档记录 | **已修**（加 `npm-publish.yml`，且"fail by design"）✓ |
| 2026-07-30 起 | 5 个 harness 全标 `runtimeEvidence: pending` | 自己标的 | **挂了 8 周** |
| 2026-09-21 | catalog 漂移 | CI 报 failure | **红了 2 天** |

---

## 二、隐含假设（Surface Assumptions）

把"这次忘了跑生成器"当成原因，是在描述症状。真正要问的是：**什么样的假设，让这个仓库必然反复出这类问题？**

| # | 隐含假设 | 为什么被相信 | 它导致了什么 |
|---|---|---|---|
| 1 | **检测到就会有人处理** | CI 报告失败是标准工程实践 | 红了 2 天无人知；`pending` 挂了 8 周 |
| 2 | **派生数据应该手工同步** | 生成物入库是常见做法 | 8 对 build/check 脚本，靠人记得跑 |
| 3 | **git 跟踪的都算"源码"** | git 跟踪 = 项目资产 | 21.6 MB 运行产物进仓库 + 进 npm 包 |
| 4 | **删掉文件就释放了空间** | "删除"的直觉 | `.git` 仍 160 MB（90 MB 死重） |
| 5 | **skill 越多越好** | 丰富的库 = 更强的产品 | 712/834 未被引用，但都在付 CI 与打包成本 |
| 6 | **单人项目不需要写入互斥** | 只有我一个人 | 两个 agent 并行 push → ADR 编号撞车 + 内容重复 |

---

## 三、第一性真相（First Principles）

### F1 · 人和 agent 只执行**被强制**的动作，不执行**被建议**的动作

这是最硬的一条，而且**你自己的仓库已经验证过它一次**：

```
npm 发布事故（已修）
  ✗ 没有 workflow          → 什么问题都没解决
  ✓ 加 npm-publish.yml     → 且刻意让它 "fail by design rather than silently skipping"
                            → 问题消失

catalog 漂移（未修）
  ✓ 有 CI 检测             → 但分支无保护、Pages 照样部署
  ✗ 没有阻断               → 红了 2 天
```

**同一个仓库，同一个教训，一次学对了、一次没学。** 差别只在"有没有把该做的事变成会失败的命令"。

### F2 · 任何"需要记得做"的步骤，失败率随频率累积

```
p = 单次遗漏概率     n = 执行次数
至少漏一次的概率 = 1 − (1−p)^n
```

加 skill 是**每周级**动作，而每加一个要同步 **8 对 build/check**。**n 增长很快 → 必然漏一次。**

这不是纪律问题，是算术。

### F3 · 派生数据的价值 = 它的消费者数量。消费者为 0 时，同步它是纯成本

核实结果（`grep -rln skill-index.json`）：

```
catalog/skill-index.json 的消费者：
  scripts/build_skill_catalog.py            ← 生成器自己
  scripts/build_original_skills_index.py    ← 生成器
  scripts/build_skill_taxonomy_evaluation.py← 生成器
  tests/test_skill_catalog.py               ← 测试
  tests/test_skill_taxonomy_evaluation.py   ← 测试
  ────────────────────────────────────────
  运行时/站点消费者：无
```

**这份数据的消费者是"生成它的脚本"和"检查它是否最新的测试"。** 这是一个闭环 ——
它的存在理由是**证明自己是最新的**。

> ⚠️ 这不等于"它没用"：`catalog/README.md` 是给人浏览 skill 库的页面。
> 但它**不是任何程序的输入**，所以"必须随源码同步入库"这个要求是可以商量的。

### F4 · git 对象库是 append-only；只有重写历史能回收

这是 git 的数据模型，不是工具缺陷。**删除工作区文件对 `.git` 大小的影响 = 0。**
证据：90 MB 早已从工作区消失的对象仍完整躺在 `.git` 里。

### F5 · 并行写入者之间需要互斥，冲突概率随并发度上升

单人项目 ≠ 单写入者。当前有 **2 个 agent 并行直接 push main** —— 这次已经撞了 ADR 编号。

## 四、重建解法（只从上述第一性推导）

### 由 F1（人只做被强制的）→ 把"记得做"变成"不做就失败"

| 解法 | 强制度 | 成本 |
|---|---|---|
| **`npm run build:all`** —— 一条命令跑全部 8 个 build | 弱（还是要记得） | 15 分钟 |
| **`.githooks/pre-commit`** + `git config core.hooksPath .githooks` | **中（本地强制）** | 30 分钟 |
| **CI 失败时通知**（邮件/Telegram） | **中（不阻断但让人知道）** | 20 分钟 |
| **branch protection** | **强** | 5 分钟，但会挡住直接 push main |

> **注意**：`package.json` 里 8 个 `build:*` **已经存在**，缺的只是把它们串起来 + 自动触发。
> 这不是"要开发新东西"，是"把已有的接上"。

### 由 F2（"记得做"是债）→ 消除步骤本身，而不是更好地执行

**既然 catalog 不是任何程序的输入（F3），那最深的解法是：让它不必入库。**

```
现状：改 skill → 人记得跑生成器 → 提交生成物 → CI 校验生成物是最新的
可能的形态：改 skill → CI 构建时生成 → 只在发布时打包
         （仓库里不再存派生数据 → 没有"同步"这件事 → 没有漏的可能）
```

这条路更大，但它**从根上消灭了这类问题**，而不是降低它的概率。

### 由 F3（消费者为 0 = 纯成本）→ 先问"这份数据谁用"

对 8 份派生数据逐一问：**除了测试和生成器，还有谁读它？**
没有消费者的，考虑改为构建时生成而非入库。

### 由 F4（历史不可逆）→ 止损，不重写

- **停止新增**：gitignore 运行产物（`skills/*/data/`、`*.jsonl`、scan JSON）
- **清理现有**：删 21.6 MB（16.33 MB 回测 dump 已核实结论无损）
- **不重写历史**：90 MB 死重的回收代价（所有协作者重克隆）> 收益，且会打断并行工作线

### 由 F5（并行需互斥）→ 给两个 agent 定规则

- 改动前先 `fetch` + `rebase`
- 或分工域：一个只改 `skills/`，一个只改 `docs/`
- 或引入 PR 流程（这也是 branch protection 的前提）
